# RFC: languages (i18n), English only to start

**Status:** groundwork done, English only (Kai, 2026-10-29: "we could do the transformation to support it but
still only have en for now"). What's left is three tasks of their own, at the end of `i18n-finish` below.
- **Built:** `i18n-setup` (1.1.1).
  - Lives in `frontend/src/i18n/`, `locales/en/`, `utils/format.ts` and `i18next.d.ts`.
  - It's tested on a `selftest` namespace that only the self-tests use, so no real UI string
    is involved yet.
- **Built:** `i18n-shadow` (1.1.2), `src/i18n/shadow.ts`.
  - **Shadowed so far:**
    - the menu (items and headings, keyed from typed maps in `nav.ts`);
    - the theme tooltip;
    - the footer's backup link;
    - Today's group badge (a count and a value) and its date (a format helper);
    - the reply habit and "longer than usual" (plurals);
    - How it works' "Start from Today" sentence (`<Trans>`).
  - **Where it runs:** on in dev, and switchable in a built app with `?i18n=shadow` /
    `?i18n=off`.
  - **Under test,** a mismatch throws.
  - **Keys:** typed as `TextKey` (`"namespace:key"`), built from the English files.
  - **Checked live** in the built app: every shadowed key matched.
  - **Tests:** `src/i18n/shadowed.test.tsx` checks every shadowed string with the inputs the
    app gives it. How it works' copy of its sentence is checked against what it renders.
  - **Bundle cost:** i18next, react-i18next and the English files are now loaded and set up
    at start-up, even with shadow mode off. With shadow mode off, a shadow call costs one
    boolean check.
- **Built:** `i18n-shell` (1.1.3): the first area cut over to `t()`.
  - **What moved:**
    - the header (name, menu button, New application, search, help, theme);
    - the menu (items and headings);
    - the footer (connection status, local-first line, backup link and hint);
    - Not found;
    - the shared delete button, rename dialog, the dropdown's "+ Add" option, and the
      duplicate warning.
  - **How:** shadow calls first (every key matched in tests and live), then `t()`.
  - **Lint:** `i18next/no-literal-string` is on for those files (`TRANSLATED` in
    `eslint.config.js`).
    - It covers JSX text, template strings, and the props people read or hear (`label`,
      `*Label`, `placeholder`, `aria-*`, `title`, `description`, `error`, `hint`, `empty`,
      `confirm`, `nothingFoundMessage`…).
    - The header's buttons moved to `HeaderButtons.tsx` so it covers them; How it works' text
      moves with Today.
  - **Tests:** `components/Shell.test.tsx` pins their English, including every tooltip, both
    theme labels and all six shapes of the duplicate warning. `CreatableSelect`'s "+ Add" was
    checked in a real browser, because jsdom won't type into Mantine's search box.
  - **Not moved:** text that callers pass in (a page's delete confirmation, a dialog title)
    moves with that page. `Placeholder` and the page descriptions in `nav.ts` are never shown
    (every page is built), so they're left.
- **Built:** `i18n-today` (1.1.4).
  - **What moved:** Today, To-dos (`todos` namespace, used on every page with to-dos), the
    reply and chase buttons, ghost and favourite marks, and reply habits (`people`). Also
    How did it go?, At a glance (`utils/attention.ts`), How it works (each step a `<Trans>`),

  - **How:** cut over directly, not shadowed first. `scripts/i18n/text_snapshot.py` recorded
    every page's text and labels on main and on the branch, over 26 views including dialogs
    and menus. `text_diff.py` showed **0 differences**. `components/TodayText.test.tsx` pins
    what the snapshot can't reach.
  - **Still English on purpose:** "Followed up" and "No reply", which are saved into your data
    as an event summary and a stage-move note (`i18n-events-activity` gave them messages). Stage names in the pipeline
    and badges are your data. The Happened button, role lines and call times move with their
    own areas.
  - **Shadow calls:** none are left; `shadow.ts` stays until `i18n-finish` in case an area wants
    it.
  - **One deliberate change** (Kai: "english dates should be 31st October 2026 (day month year),
    american is month day year"):
    - every date goes through the dayjs patterns in `utils/format.ts`, not the browser's Intl
      locale, so "31 Oct 2026" and a 24-hour clock everywhere. `utils/time.ts` and
      `Interviews.tsx` are routed through it. Intl's en-GB was tried first, but it writes
      September as "Sept" where dayjs writes "Sep", so one month came out two ways;
    - date inputs show "D MMM YYYY", and date-and-time pickers "D MMM YYYY HH:mm" (they showed
      "30/10/2026 19:25") (`theme.ts`);
    - calendars follow the chosen language (`DatesProvider` with `dayjsLocale()` in `App.tsx`).

    The text snapshot was taken before this; the dates are the only difference since.
  - **Calendar month and day names** come from dayjs's locale data, not the text files, so the
    pseudo-language can't accent them. They'll change with a real language's dayjs locale
    (`multi-language`).

    pass a `TFunction<"namespace">` instead.

    words (a call named "Intro <platform> chat") would be taken for a tag. Your words go in
    as components (`<call/>` with `components={{ call: <>{label}</> }}`); `values` only carry
    what the app builds, like dates.

    IR35"), not a translated word dropped into a placeholder.

    renders empty, so tags get their own names (`<guide>`).

    default would silently switch every later test to its language.

    English word. The theme button is `theme.toDark` / `theme.toLight`, not
    `"Switch to {{mode}} mode"`, because "dark" and "light" need translating too.

    (`"common:nav.items.today"`), while bare keys and unions of them type-check. So typed maps
    hold bare keys, and the unused-key scanner counts dotted strings.

    `version`, so the footer said "vundefined". The value is passed as `String(version)` to
    keep the old output exactly.

    than a shadow call per string: it covers every string a page shows, including ones no
    test looks at.
  - A component rendered on its own in a test needs `src/i18n` loaded. The test setup imports
    it, and so does `main.tsx`, which used to get it only by way of shadow mode.
  - `t()` from `useTranslation("todos")` refuses another namespace's keys too. A component
    that needs both uses `useTranslation(["todos", "common"])`.
  - A Mantine `Tooltip` inside `Menu.Target` takes the menu's `aria-haspopup` and
    `aria-expanded` for itself, so the button never says it opens a menu. The tooltip goes
    outside: `<Tooltip><Menu.Target><ActionIcon/></Menu.Target></Tooltip>`.
  - The lint plugin builds its word filters without the Unicode flag, so `\p{L}` doesn't mean
    "letter". A first try at "skip text with no letters" skipped everything; it's now
    `[^A-Za-z]*`, and was checked by putting a hard-coded label back.

## The questions, answered

### 1. Is the groundwork a version bump?

All 14 groundwork PRs are **patches**: the code changes, but what people see doesn't. That
includes:
- the shadow mode, an opt-in console aid;
- the API's new `code`, `params` and `msg` fields, which are additive and need no data
  migration (see 4a).

Shipping the first new language with a switch is a **minor** bump. None of it is breaking:
nothing is removed or renamed, and no saved data is rewritten.

**Releases** (Kai, 2026-10-29: "yes add release for each change"): every one of the 14 PRs is
released as its own patch version, as `CLAUDE.md` says for every version.

### 2. Which library?

**i18next + react-i18next**, as the roadmap already says:
- the most widely used and documented option;
- plurals through `Intl.PluralRules`, so Chinese (no plural forms) and Polish (several) both
  work;
- `<Trans>` for sentences with links or bold text inside them;
- languages loaded only when chosen;
- TypeScript can check keys, so a typo in a key fails `pnpm typecheck`.

Also considered:
- **Lingui** keeps the English inline (`` t`Waiting to hear back` ``), which reads nicely,
  but the English text *is* the key, so rewording English silently drops every translation
  of it.
- **FormatJS** (react-intl) is good but heavier for our needs.

### 3. How are keys organised?

- **One namespace per area:** `common`, `nav`, `today`, `applications`, `board`, `roles`,
  `people`, `documents`, `insights`, `timeline`, `errors`.
- **Files:**
  - English is the source of truth, written as TypeScript: `frontend/src/locales/en/<namespace>.ts`,
    with `as const` (see 3a for why).
  - Other languages are JSON (`frontend/src/locales/<lang>/<namespace>.json`), the format
    translators and translation platforms expect.
- **Keys** say what the text is for, not what it says: `today.waiting.usuallyReplies`, not
  `usuallyRepliesWithinNDays`. Then rewording the English keeps every translation of it.
- **English is bundled**, so it's always there as the fallback. Other languages are loaded
  only when chosen.
- **Wording decisions stay in the English file and in tests.** For example, "Passed" is never
  a Sankey label, and *Decided not to apply* is used instead.

### 3a. From a component to its text, and type checking

**The English file** (`locales/en/today.ts`) is a nested object of strings. Placeholders are
in `{{ }}`, and plurals are `_one` / `_other` keys:

```ts
export default {
  waiting: {
    title: "Waiting on them",
    // Reply habit under a person; days are working days (domain/replies.py).
    usuallyReplies_one: "Usually replies within {{count}} working day",
    usuallyReplies_other: "Usually replies within {{count}} working days",
    slower: "{{name}} is taking longer than usual",
  },
} as const;
```

**Registered once** (`src/i18n/index.ts`). English is bundled, other languages are loaded when
chosen, and English is the fallback:

```ts
import today from "./locales/en/today";
export const resources = { en: { today /*, common, insights, … */ } } as const;
i18n.use(initReactI18next).init({ lng, fallbackLng: "en", resources, defaultNS: "common" });
```

**Typed once.** This is what makes every key checked:

```ts
declare module "i18next" {
  interface CustomTypeOptions { defaultNS: "common"; resources: (typeof resources)["en"] }
}
```

**In a component:**

```tsx
const { t } = useTranslation("today");
<h3>{t("waiting.title")}</h3>
<Text>{t("waiting.usuallyReplies", { count: days })}</Text>
<Trans t={t} i18nKey="waiting.slower" values={{ name }} components={{ b: <b /> }} />
```

**Outside components** (hooks, toasts, `utils/`): `i18n.t("errors:title")`
from `src/i18n`.

**How a lookup works at run time:**
1. i18next takes the current language, the namespace (`today`) and the key path
   (`waiting.usuallyReplies`).
2. With a `count`, it asks `Intl.PluralRules` which form the language uses (`one`, `other`,
   or `few` / `many` for some languages), and picks that suffix.
3. If the key is missing in that language, it falls back to English.
4. It fills in `{{count}}`.

React escapes the result like any other text.

**What the type checker catches** (`pnpm typecheck`, in CI too):
- A key that doesn't exist (`t("waiting.titel")`), or one in the wrong namespace: an error.
- Autocomplete of keys in the editor.
- Plural keys used without their suffix (`t("waiting.usuallyReplies", { count })`), which type
  correctly.
- Interpolation values: because the English is `as const`, i18next reads `{{name}}` from the
  string itself, so a misspelt value name is an error. That's why English is a `.ts` file: a
  `.json` import widens every string to `string`, which keeps the keys but loses the
  placeholders.
- **Tried on 2026-10-29** with i18next 26.5 and react-i18next 17.1:
  - a wrong key and a wrong value name both failed `tsc`;
  - plural keys typed correctly;
  - but a call with no values object at all (`t("hello")` for `"Hello {{name}}"`) passed.

  That gap is covered at run time: a `missingInterpolationHandler` throws in tests and dev.

**What it doesn't catch, and what covers it:**
- **Keys built at run time** (`` t(`stages.${id}`) ``) can't be checked. Avoid them: map ids
  to keys in a typed object (`const SOURCE_LABEL = { "source:recruiter": "sources.recruiter", … } satisfies Record<SourceId, InsightsKey>`),
  so a new id without a label is a type error.
- **Unused keys** (left behind after a change): a test lists keys in `en` that no code uses,
  with a small scanner (`src/i18n/catalog.ts`). Keys in typed maps are written bare, the way
  that file's `t()` takes them (`"nav.items.today"`), and the scanner credits any dotted
  string to the file's namespaces. It doesn't understand `keyPrefix`, so the app doesn't
  use it.
- **Keys with no text at all** (a cast past the types, or a plural called without `count`):
  strict mode throws `MissingKeyError` in tests and dev.
- **Other languages:**
  - Keys `en` doesn't have fail a test.
  - Missing keys, namespaces and plural forms fail the test (Kai: "it would be a bad bad error
    if one is missing"). Only at run time, a gap that slipped through would show English.
  - A translation that drops a `{{placeholder}}` fails a test.
- **Hard-coded English** in converted areas: the lint rule (`no-literal-string`).
- **Wrong English:** tests still look for the real words, because they run in English.

**In the editor:** the i18n Ally extension for VS Code (optional) shows the English inline
next to `t("…")`, and jumps from a key to its string.

### 4. What about text the backend writes?

**The backend never translates.** All translating happens once, in the frontend. The
backend's only change is to send a code or id, and the values, *next to* its English, so the
frontend can look them up.

Translating in Python too (gettext or Babel, reading `Accept-Language`) was rejected. It
would mean i18n twice: two catalogs, two toolchains and two sets of plural rules for
translators. And it still couldn't translate history that's already saved in English.

The backend writes three kinds of English, and each gets its own fix.

- **Error messages** (`i18n-errors`). Errors people see gain a `code` and `params`, e.g.
  `{"detail": "A company with applications can't be deleted.", "code": "company_has_applications", "params": {"count": 3}}`.
  - The frontend shows `errors:codes.<code>` when it has it, and otherwise the English `detail`.
  - `detail` stays, so curl, the CLI, logs and `jat mcp` keep reading English.
  - Errors people never see (internal, "can't happen") can stay English-only. So does the
    framework's 422 validation text; forms mostly catch those problems before sending.
  - FastAPI doesn't put error bodies in the schema, so `i18n-errors-setup` declares them there;
    without that the `code` Literal would never reach `schema.d.ts`.
- **Computed labels** (`i18n-sankey`, `i18n-insights-tabs`). The API already sends ids (`source:recruiter`,
  `holding:applied`) beside the English name. As built, the frontend translates by a separate
  `code` on the nodes the app names, not by id: one diagram's `applied` isn't a stage.
  - Stage names are the exception: they go by id and name together (see 5).
  - Timeline entry titles are built in the frontend from a `kind` and raw fields
    (`i18n-timeline-titles`, `i18n-timeline-records`). The API sent neither when this was
    written: entries had no `kind`, and rounds, calls, offer replies, stage moves, notes and a
    person's closed reason lacked fields. Both are added next to the English `title`, which stays for older clients.
- **Saved event summaries** (`i18n-events`). This is the hard one: the text is saved in the
  database, the JSONL export and git.
  - **What an event is:** one row in the `events` table (`Event` in `db/models.py`), and one
    line of an application's history. Every entry on the application's timeline is one, as
    is much of the Timeline page.
  - **Kinds:** a stage move, a call, an email attached, a note added, a file, an interview, or
    a manual entry (*Log activity*, links, CVs sent).
  - Events are append-only, and they're exported to `export/events.jsonl`, so they're in
    your data repo's git history.
  - Each has a `kind`, the stages it moved between, an English `summary` and a free-form
    `data` field.
  - **Summaries come from two places.** Some are written by the app ("Link added: Contoso
    careers", "CV sent: …", "Note added: …", an email's "(from …)"). Some are typed by you
    (*Log activity*).
  - Only the app-written ones get a message key. Yours are your words, like a note, and are
    shown as you typed them.
  - New events also save the message as data: `data.msg = {"key": "event.linkAdded", "params": {"title": "…"}}`.
  - The English `summary` stays, so search, the export and `git diff` stay readable.
  - Both timelines show `msg` when there is one, and otherwise `summary`.
  - Old events stay as they are (see 4a).

**What's duplicated is some English, not the system.** A user-facing error's English lives in
both the Python `detail` and the frontend's `errors` file. That's fine:
- the app always shows the frontend's text;
- a test checks every code has a key;
- if the wording of the two copies drifts apart, nothing breaks.

**Type checking across the API.** This uses the chain that already guards every API type:

```
Python Literal  →  openapi.json  →  schema.d.ts  →  tsc
                   (jat.openapi)    (gen:api)      (pnpm typecheck)
```

`tests/test_openapi.py` fails if `openapi.json` is stale.
- **Error codes:** `code: Literal["company_has_applications", …]` becomes a TypeScript union
  `ErrorCode`, and `locales/en/errors.ts` is `as const satisfies Record<ErrorCode, string>`.
  A code with no text, or text for a removed code, fails `pnpm typecheck`.
- **Fixed nodes** (holding, source, *Decided not to apply*): the same, with a `NodeCode` Literal.
  As built, a Sankey node carries an optional `code` (translated) next to its `name`; a stage has no
  code and goes through `stageName`. `i18n-sankey` above says why fixed nodes aren't by id.
- **Saved messages:** the event response's `msg` is a union keyed by `key` (a Pydantic
  discriminated union, each with its own params model). TypeScript then knows that
  `event.linkAdded` comes with a `title`.
- **What types can't promise:** data already on disk. An event whose `msg` doesn't match the
  model (older, or written by a newer version) is sent as `msg: null`, and the frontend shows
  the English `summary`.

### 4a. What happens to the data you already have

**Nothing is rewritten. There's no migration and no change to the database schema.**

- **Your own words** (companies, roles, people, notes, to-dos, stage names in `config.toml`)
  are never touched or translated.
- **Events already saved** keep their English `summary` exactly as it is. They show in English
  whatever language the app is in.
- **New events** written after `i18n-events` get one extra entry inside `data`, the
  free-form JSON column events already have (beside `implied` and `bookkeeping`), so no
  new column. For example, `"msg": {"key": "event.linkAdded", "params": {"title": "Contoso careers"}}`.
  - The English `summary` is still written as before.
  - Those event lines in `export/*.jsonl`, and so in your data repo's git diffs, are a little
    longer. Nothing else in the export changes.
- **Going back to an older version** is safe: older code ignores keys it doesn't know in
  `data`.
- **Choosing a language** is a browser setting (localStorage), not data, so it's not in the
  database, the export or git.

**The backfill: skipped** (Kai, 2026-10-29: "yes skip the backfill"). "Backfilling" means a one-off migration that goes
through events *already saved* and adds `data.msg` to them by recognising their English
`summary`. For example, it would spot that `Link added: Contoso careers` has the shape
`Link added: {title}` and add `{"key": "event.linkAdded", "params": {"title": "Contoso careers"}}`.
Only then could old history show in another language. It's skipped because:
- it rewrites every old event line in the export, which is one big git diff of your history;
- it only works where the English is unambiguous. A note or link titled with a colon in it,
  or a summary from an older wording, could be guessed wrong;
- it buys little: old history is in English, which is the only language you use.

It stays possible later, as its own PR with a data-safety review. It would only ever *add*
`msg`, never change `summary`, and would leave alone anything it can't match for certain.

### 5. Do your own words get translated?

No. Notes, company names, to-dos, stage names you've renamed or added, and everything else you
typed are your data, shown as you wrote them. A default stage you haven't changed does translate.
- **The default workflow:** a new data folder's `config.toml` could be written in the chosen
  language when it's created (`jat init`). Stage ids stay English (`applied`), so the logic
  that keys off ids keeps working.
- **Existing data folders** keep their names.
- **The default stages show in your language** (`i18n-default-stages`, decided 2026-10-30).
  - Kai, seeing English stage badges under the pseudo-language: "stages are still in english".
  - Of two options (always as written, or translate only the defaults), Kai chose the
    second: "yes option 2".
  - **The rule:** a stage whose id and name are both still the default pair (`applied`,
    "Applied") is shown with the translated name.
  - **Renamed or added stages** show exactly as written in `config.toml`, which never changes.
  - **The words were the app's, not yours,** so translating them doesn't touch your data.
- **Logic that looks for "interview" in a stage's name** (the board's round columns) should
  look at the id instead, or a translated name stops matching.

### 6. Where is the chosen language stored?

In the browser (localStorage `jat.language`), defaulting to the browser's language, then
English.
- Storing it in `config.toml` would make it follow the data folder across machines, but the
  UI can't write `config.toml`, and two people never share one tracker anyway.
- Revisit for `hosted-version`, where it becomes a per-account setting.
- The switch in the header has been there since 1.2.0 (`i18n-switcher`): English, and *Coming
  soon!* until a second language ships. A dev-only `?lang=` parameter helps testing.

### 7. Dates, numbers and money

- **Dates:** load the matching dayjs locale and use the locale's formats (`LL`, `ll`, `LT`,
  or `Intl.DateTimeFormat`) rather than fixed `D MMM`. `YYYY-MM-DD` stays for values sent to
  the API.
- **Calendars:** Mantine's `DatesProvider` gets `locale` and the locale's first day of the
  week (Monday in the UK and China, Sunday in the US).
- **Numbers:** `Intl.NumberFormat(locale)` instead of the fixed `toLocaleString("en-GB")`.
- **Money:** the offer's own currency stays as it is. Only the formatting follows the
  language.
- **Working days:** reply times count weekdays only, which is right for UK and Chinese working
  weeks. Bank holidays are already noted as missing.

### 8. Plurals and sentences built from pieces

- **Plurals:** the ~48 hand-built plurals become i18next count keys (`_one`, `_other`).
- **Sentences:** some are glued together around values or links ("Usually replies within
  **3** working days", a count beside a link). They become one key with
  placeholders, or `<Trans>` when there's markup inside, so translators can reorder them.
  No more joining fragments.

### 9. Layout and fonts

- **Chinese:**
  - it's denser and has no spaces, so long strings need `word-break` / `overflow-wrap`
    checks;
  - it needs a CJK font. Use the system's (PingFang, Microsoft YaHei, Noto Sans CJK) through
    the font stack, and never a web font, which would break "the app never calls out to the
    web".
- **German and similar** are ~30% longer: buttons in Today's rows and table headings need
  checking at 375 px.
- **Right-to-left** (Arabic, Hebrew) isn't in scope. Use logical CSS properties
  (`margin-inline-start`) where code is touched anyway, but don't promise it.

### 10. Search

Search folds case and accents and splits the query on spaces (`domain/search.py`), then looks
for each piece as a substring. A Chinese query without spaces still works as a substring.
Mixed-script search and Chinese pinyin aren't planned.

### 11. Tests

- **The 149 frontend tests** find things by English text. Run them in English: the test setup
  loads the English bundle synchronously, so they keep passing and keep checking real
  wording.
- **Completeness:**
  - Every key used in code exists in `en`: the type check covers typed calls, and strict mode
    throws for anything else the tests run.
  - Every other language has no keys `en` doesn't have.
  - Every other language has every English key and namespace, and every plural form it needs
    (`Intl.PluralRules(lang).resolvedOptions().pluralCategories`); anything missing fails.
- **A lint rule:** `eslint-plugin-i18next`'s `no-literal-string`, switched on folder by
  folder as each area is converted, so new hard-coded English can't sneak back in.
- **A backend test:** every error `code` the API can return has an `errors.<code>` key.

### 12. How do we know the conversion is complete with only English?

A **pseudo-language**, dev-only, with `?lang=pseudo`. It turns every string into accented,
~35% longer text in brackets ("[Ŵàîţîñĝ ţö ĥéàŕ ƀàçķ ·····]"). Anything still in plain
English was missed, and anything that overflows will break in German.
- Screenshot every page in it with Playwright as each area is converted.
- This is how the groundwork gets checked without a translator.

### 13. Who translates, and how?

- **First version:** Claude drafts the JSON files and a native speaker reviews them before
  release. A wrong translation is worse than English.
- **Later:** a translation platform (Weblate is free for open source, or Crowdin) so other
  people can contribute. That's outward-facing, so it needs Kai's yes.
- `CONTRIBUTING.md` gets a "Translating" section once a second language exists.

### 14. Docs, README, website and CLI

- **Translated with the first new language:** the README (as `README.zh-CN.md`, linked at
  the top) and the website, using Astro's i18n routing.
- **English only:** the guide (`docs/guide/`) stays English; translating it doubles the upkeep
  of every PR's docs step and goes stale fast. The CLI, `llms.txt`, the API docs and commit
  messages stay English too.
- Screenshots stay English.

     declaration.

## Difficulties, ranked

1. **Saved English in events.** The history in your data folder and git is English and stays
   English. Only new events can be translated reliably.
2. **Volume and churn.** ~12,800 lines to touch while features keep landing. Each converted
   area needs its lint rule on straight away, or new English creeps in. Parallel feature PRs
   will conflict; convert one area at a time and merge quickly.
3. **Sentences built from pieces**, and plurals: the work there is restructuring, not just
   wrapping strings.
4. **Wording rules** that live in people's heads ("never *Passed* in a Sankey", "Not a ghost",
   not "undo") now live in a JSON file. Comments in `en` keep the why next to the string.
5. **Stage names** are user data, but defaults are created in English, and some logic
   matches on names ("interview"). Ids, not names, must drive behaviour.
6. **Translation quality** with no native speaker on the team. It needs a reviewer before
   release.
7. **Layout:** long German, dense Chinese, CJK fonts without a web font.
8. **The upkeep tax:** every future PR adds keys to `en` and (once there is one) leaves other
   languages to catch up. The completeness test makes that visible rather than silent.

## Not doing

- Translating your own data.
- Machine translation inside the app ("No AI").
- Right-to-left layouts.
- Translating the guide, the CLI or `llms.txt`.
- Detecting language from location.
- A web font for CJK.
